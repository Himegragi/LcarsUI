# 安全宿主交接原型（用完即丟）

**這不是正式框架程式碼，也不是 API 提案。** 不會實際終止程序；「宿主選擇退出」只會被記錄。

## 問題

> 共享邏輯狀態變得不可信、但已**宣告**有安全的宿主交接路徑時，框架能否可靠地：讓受影響範圍保持不可用、只送出一則宿主通知、讓獨立的工作繼續、安全處理晚到結果，而且不讓舊實例復活？

依據：ADR 0002（多個 UI 執行環境、共享服務所有權）、ADR 0003（錯誤回報、例外邊界、受限收尾、明確重建、安全交接政策），以及 `docs/research/unrecoverable-fault-boundaries.md`。

## 一個指令

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File prototypes/safe-handoff/run.ps1 -Scenarios     # 自我檢查情境
powershell.exe -NoProfile -ExecutionPolicy Bypass -File prototypes/safe-handoff/run.ps1 -BuildOnly
powershell.exe -NoProfile -ExecutionPolicy Bypass -File prototypes/safe-handoff/run.ps1 -Interactive   # Win32 視窗
```

檔案：`handoff_model.hpp`（模型）、`main.cpp`（情境與 Win32 外殼）、`CMakeLists.txt`（C++26、`/utf-8`、`/EHsc`）、`run.ps1`。`build/` 不納入版本控制。

## Fixture 假設（模型的輸入，不是偵測結果）

- `FaultSpec` 由情境直接宣告：回呼拋例外後，必要狀態是否仍有效、受影響的共享服務是哪個、相依是否已知、交接路徑是否安全。模型**不**偵測記憶體破壞，也不判斷 UB。
- 每個環境是否「宣告隔離」也是輸入。相依未知時，影響範圍擴大到所有**未宣告隔離**的環境。
- 收尾是否安全（`cleanup_safe`）是輸入，預設為安全。
- 容量都是探索用的數值：實例 4 個、日誌 80 行、診斷 4 筆、非同步結果槽位 6 個。宿主通知佇列的上限等於實例上限，因為每個實例最多只轉換一次故障。

## 對應的已核定政策

- 公開擴充回呼的 C++ 例外在 `dispatch` 攔截；但攔截本身不證明安全，是否停止由 `FaultSpec` 決定。
- 不可用的實例會立即拒絕所有模擬的普通路徑：設值、啟動工作、重建目標、派送。實體收尾只在安全點進行。
- 宿主通知只在**擁有者執行緒**、而且沒有回呼或遍歷進行中時送出。通知的內容是複製出來的（環境名稱、實例 id），不借用實例指標。
- 每次故障轉換只有一則通知；同一個故障世代的重複嘗試，只計數、不再通知。
- 宿主回呼的回覆不代表「成功」或「恢復」。回呼內嘗試操作 A、派送或再次遞送，都會被拒絕，不遞迴、不死結。
- 宿主回呼拋出例外時，只在宣告的宿主邊界攔截，記錄為「交接失敗」，不重試，也不視為宿主已確認。這裡不發明任何致命處理政策。
- 診斷是可選的：停用、已滿、拋例外，都不影響必要的故障狀態和宿主交接；拋例外的接收器會被停用。
- 晚到結果：結果槽位在啟動工作時就已預留，結果送達後在擁有者執行緒結算，槽位一定歸還。
  - 實例不可用：不更新 UI，只結清收尾。
  - 實例還在執行，但目標世代不符：不更新（和「不可用」分開計數）。
  - 實例已退休：只歸還槽位。
  - 外來、重複、過期的 token：直接拒絕，不配置任何儲存。
- 明確重建：建立新的實例 id 和新世代；舊實例不會被重設成執行中，而是繼續等待收尾，結清後才退休。
  - 下列情況拒絕重建：隔離或資源條件不成立、共享服務仍不可信、實例容量已滿。
  - 共享服務必須由宿主**明確**替換，不會被默默修復。
- 未宣告安全交接路徑時，標記為「超出範圍」：不通知、不宣稱恢復、不重建。致命路徑不在本原型的範圍內。

## v5 修正（審查後；紅燈→綠燈）

紅燈：`evidence/scenarios-v4-red-review.log`，用 v4 模型跑新增的情境 29–33，failures=14（132 PASS）。

- **列管工作身分**（情境 29）：`WorkToken` 多了一個永不重用的 `work` id；每個指派最多 4 項未結束工作（有上限，不記完成歷史）。重複 `end_work` 被拒，不會扣到另一項；第二項沒結束前不能生效；取消後重新要求、交接槽位重用後都正確。
- **宣告不安全的回呼失敗**（情境 30，並更新情境 23）：`post_throw_safe=false` 現在在確認前、確認後都一樣處理，會標記超出範圍（只是負面標記，沒有致命處理）。已確認的確認保留，但額度保留；`deliver()` 同一輪不再呼叫下一個回呼；`begin_work`／`end_work`／`reassign`／`cancel_reassign`／`activate`／`process_control` 都不改狀態，信箱不清空。
- **非擁有者執行緒**（情境 31）：`reassign` 在動到任何計數前就拒絕。所有新控制入口從另一條執行緒呼叫後，比對狀態、所有計數、日誌長度、信箱、接收者版本，全部不變。
- **空的接收回呼**（情境 32）：`add_receiver` 拒絕空的 `std::function`，`receiver_alive` 也會檢查；刻意不確認的接收者仍然有效。
- **交接表已滿時重複回報**（情境 33）：`fault()` 先找出「這次真的新變成不可用」的實例；沒有的話只計數，不配置紀錄、不拋例外。`service_fault` 回傳 `RefusedUnavailable`。
- **`old_work_ended`**：v4 初版排除了 `h.current`，但改派受理後被撤銷的舊指派仍是 `h.current`。這在 v4 證據之前就已修正（改成檢查所有指派）；情境 24、29 直接檢查「舊工作沒結束時拒絕生效、結束後才成功」。
- 範圍限制：額度是**邏輯數量**的保證，不代表記憶體配置不會失敗；晚到結果的 worker 仍然用合作式等待（有上限的逾時只是防卡住）。v3 證據因**語意變更**而被取代（見 `evidence/SUPERSEDED-v3.txt`）；v1、v2 見 `evidence/SUPERSEDED-v1.txt`。下方「對應的已核定政策」中關於「回呼拋例外即視為已嘗試、歸還額度」與「沒有接收者時記錄失敗」的敘述，已由 v4 取代。

## v4 變更（依 ADR 0003 Q111–Q124 新決策；語意變更，不是紅燈修正）

- **必須先有接收者**：`add_env`／`rebuild` 在沒有有效主動接收途徑時回傳 `RefusedNoReceiver`；容量已滿時在任何部分變更前拒絕（情境 20、22）。
- **計畫性撤除**（fixture 窄規則）：主動接收者仍有執行中環境、或任何接收者仍承擔未完成交接（資格、回呼中、列管工作）時，`detach_receiver` 回傳 `RefusedDependents`。`receiver_lost` 是失敗，不是撤除（情境 28）。
- **確認前失敗**：回呼拋例外或接收途徑失效時，交接保留、額度保留、範圍仍不可用、**不重送**；擁有者要明確改派（情境 11、23、28）。
- **只有明確確認算數**：`confirm(AckToken)` 是窄控制操作，可在回呼內或之後呼叫；一般返回不算。確認不讓 UI 復活（情境 22、23）。
- **身分**：`AckToken = (world, handoff, assignment)`，id 全部來自永不重用的計數器，不用指標。拒絕外來 World、已釋放（過期）、已撤銷、重複的確認。被撤銷的指派紀錄在舊工作結束後回收，交接釋放後整筆清空；沒有完成歷史清單（情境 24、26）。
- **改派**：`reassign` 受理時立刻撤銷舊資格；`activate` 是擁有者執行緒上的明確提交，要先等舊指派的回呼與列管工作（`begin_work`/`end_work`）結束，並重新驗證候選的身分與版本。「可生效」不等於「已生效」（情境 24、25、27）。
- **一次一個要求**；取消回到待接管、額度保留、舊工作繼續、舊資格不恢復；取消與生效誰先在擁有者執行緒處理誰贏，另一個回報 `RefusedStale` 或 `TooLate`（情境 25、27）。
- **釋放**：只有「已確認＋相關回呼已結束＋宣告可安全釋放」三者成立才釋放，每個交接只釋放一次。確認後回呼拋例外：確認保留、另外計數、不重送；是否安全由接收者登記時的 `post_throw_safe` 宣告；不安全時額度**無限期保留**且在狀態與快照中可見（情境 23）。
- **信箱**：真實 `std::thread` 只能把控制訊息投遞到有上限的 `ControlBox`；擁有者用 `process_control()` 依 FIFO 處理（情境 27）。直接從 worker 呼叫 `confirm` 會被拒絕且不動狀態。
- **送給新接管者**：改派生效後，同一則交接會再送給新的接管者一次。這是擁有者明確安排的接管，不是自動重送；舊接收者不會再收到。
- 情境 16（v3 的不遞送循環）由情境 26 取代。

## v2 修正（審查後；紅燈→綠燈）

紅燈：`evidence/scenarios-v1-red-review.log`，用 v1 模型跑新增的情境 15–18，failures=6。當時的綠燈：`evidence/scenarios-v2.log`，failures=0，現已被 v3 取代。v1 證據已被取代（`evidence/SUPERSEDED-v1.txt`）。

- **變更入口的統一防護**：所有公開的變更入口都先經過同一道檢查，包括設值、啟動工作、重建目標、派送、新增環境、宣告服務故障、替換服務、重建、結算。
  - 非擁有者執行緒：拒絕，而且**不碰任何狀態或計數**，避免資料競爭。
  - 宿主回呼內：拒絕。
  - 結構性變更（新增環境、替換服務、重建）在派送或遍歷進行中一律拒絕。這是本原型的 fixture 規則，不是正式的安全點設計。
  - 情境 15 用實際狀態證明：回呼內的重建、新增、結算、替換服務、宣告故障都沒有生效（實例數、槽位、服務信任狀態、B 的狀態都不變）；非擁有者執行緒的設值被拒絕，值和計數都不變。
- **通知額度**：每個執行中的實例都預先持有 1 個「未來故障通知」的額度。故障時，額度轉移到待送通知；通知遞送後才歸還。實例退休不會歸還額度，因為它的通知可能還沒送出。
  - 所以「待送通知數 ≤ 已用額度 ≤ 4」恆成立；額度用完時，新增環境或重建會被明確拒絕，不做任何部分修改。
  - 原本的 `logic_error` 已移除。不同的故障轉換**不會**被合併，容量也**不會**動態成長。
  - 情境 16：做 8 輪「故障→替換→重建→退休」而不遞送。受理 4 次故障轉換、拒絕重建 5 次、最大待送通知 4。遞送後送出 4 則通知，快照世代分別是 1、2、3、4，其中 3 個舊實例已經退休；之後額度完全回收，重建成功。
  - 這和情境 10 不同：情境 10 是對**同一個**故障世代重複嘗試 1000 次。
- **錯誤預留世代**（情境 17）：對一個**仍在預留中**的槽位，送出世代錯誤的 token。結果被拒絕、槽位仍是預留中，之後有效的發布照常成功。v1 情境 8 裡會混淆原因的那個檢查已經刪除。
- **超出安全交接範圍**（情境 18）：`settle` 拒絕結算，已發布的結果和預留都保持原狀，不更新 UI，也不釋放；普通操作同樣被拒絕。這個狀態**刻意保持未解決**：不實作致命路徑，也不釋放仍在進行的工作。
- **互動模式**：
  - 新增「▶ 下一步」按鈕，三個引導情境各有不同的有序步驟。
  - 狀態列顯示：下一步要做什麼、宣告的交接與收尾是否安全（標明是 fixture 輸入）、宿主**下次**的選擇、目前狀態（「已請求退出（模擬）」或「程序保留」），以及通知額度。
  - 重設時，宿主的選擇也一併重設。

## 情境與證據（v1 紀錄；v2 全部重跑通過，見 `evidence/scenarios-v2.log`）

1. A 故障、B 獨立：A 立即不可用並拒絕所有路徑；B 繼續；回呼中不呼叫宿主；遞送後只有一則通知；回覆後 A 仍不可用；重複嘗試不產生通知風暴。
2. 共享服務故障：A、B 都不可用，獨立的 C 繼續，一則通知涵蓋兩者。相依未知時擴大到所有未宣告隔離的環境。
3. 巢狀遍歷中故障：A 立即不可用；遍歷結束前通知延後；結束後才送出。
4. 宿主回呼內重入：A 操作、派送重入、遞送重入都被拒絕；回呼結束後 B 正常。
5. 診斷停用／已滿／拋例外：都不影響必要狀態與交接。
6. 宿主保留程序 vs 模擬退出：兩種情況 A 都仍不可用。
7. 晚到結果：舊 A 不可用時只結清收尾；共享服務未替換前拒絕重建；替換後重建成新實例，舊實例仍不可用並等待收尾；重建後才到的舊結果不更新新實例；舊實例結清後退休；兩個槽位各歸還一次。
8. 重複、外來、越界的結果都被拒絕。已結算的 token 會過期，這是真正的過期世代拒絕。實例仍在執行中時，結果只因目標世代不符而被拒絕，「不可用拒絕」計數維持 0。（錯誤預留世代改由 v2 的情境 17 驗證。）
9. 重建被拒：隔離或資源條件不成立、實例容量已滿。
10. 1000 次重複故障嘗試：只有 1 則通知；日誌與診斷都有上限。
11. 宿主通知回呼拋例外：記錄交接失敗；不重試、不視為已確認；A 仍不可用。
12. 未宣告安全交接：超出範圍，不通知、不重建。
13. 回呼例外但宣告狀態仍有效：只回報失敗，不停止範圍。
14. 真實 `std::thread`：worker 只持有帳本指標和 token，不碰 UI。它在 A 不可用之後才發布結果；擁有者執行緒結算時不更新舊 A，槽位歸還；非擁有者執行緒嘗試結算會被拒絕。
    - 等待方式：worker 本身會在有限步驟內完成，擁有者用合作式的方式等它，最後 join。5 秒只是防止測試卡住的上限，**不是**強制取消的期限，也不是正確性條件。

標題寫明 v4、可丟棄、模擬。引導：1 延後確認、2 回呼內確認、3 改派（撤銷→等待→生效）、4 取消先處理、5 生效先處理、6 確認後拋例外（宣告安全）。「▶ 下一步」逐步執行；自由操作：A 回呼故障、遞送、最新／最舊憑證確認、舊工作結束、受理／取消改派、改派生效。狀態列顯示交接 id、狀態、持有額度、目前指派與確認資格、改派要求與候選、列管舊工作、額度（執行中＋保留）、釋放次數、不可用環境。每次重設都重建整個 World 與全域狀態；日誌上限 120 行。以下是 v3 的舊說明。

## 互動模式（v3 舊說明）

視窗標題寫明「可丟棄、模擬、不實際退出程序」。按鈕：

- 三個引導情境：
  - 引導 1：故障 → 通知 → 宿主保留 → 晚到結果
  - 引導 2：共享服務故障
  - 引導 3：重建與舊結果
- 自由操作：A 回呼故障、shared 服務故障、遞送宿主通知、切換宿主選擇、送達舊 A 結果、替換 A 的服務、重建 A、嘗試 A／B 操作。

狀態列顯示：
- 每個環境的世代、狀態、值、目標世代、未結工作、服務是否可信。
- 等待收尾的舊實例數、待送與已送通知數、交接失敗數、宿主選擇、是否超出範圍。
- 晚到結果的套用數和三種拒絕數、拒絕發布數、槽位使用數、拒絕操作數、重建與拒絕重建數。

下方是有上限的日誌。按鈕的處理函式都直接呼叫模型，沒有另寫一份邏輯。我沒有開啟互動模式。

## 限制

- 所有「安全」都是 fixture 宣告：宣告交接路徑安全、收尾安全、環境隔離，並不證明真實宿主或真實資源真的安全。
- 沒有整合驗證，也沒有效能驗證。
- 不是真實宿主：沒有宿主巢狀迴圈、GPU、IME、UIA。
- 不是破壞偵測器：安全與否都是宣告的輸入。只示範一般 C++ 例外，不是完整的正式例外保證。
- 不實作致命路徑，也不呼叫任何終止 API。
- 有上限的只有模型自己的容器，不代表整個程式的記憶體上限。
- 通知額度只是**數量上**的保證：它不能證明 deque 或字串的配置不會失敗，本模型也沒有驗證低記憶體時的後備路徑。
- 沒有任何整個應用層級的記憶體、效能或真實宿主保證。
- 單執行緒擁有者模型；真實執行緒只用在有限的 worker 上（晚到結果、控制信箱）。
- v4：「確認後回呼失敗是否安全」、「可安全釋放」都是宣告；不安全時沒有任何回收路徑（刻意不擴充政策）。
- v4：計畫性撤除只實作「有相依就拒絕」的窄規則，沒有實作「相依環境先完成收尾」的流程。
- v4：每個交接最多 4 筆指派紀錄；舊工作一直不結束時，再次改派會被拒絕（明確回報，不成長）。
- v4：信箱上限 16 則，滿了 `post` 回傳 false，由投遞端處理；情境沒有測滿載。
