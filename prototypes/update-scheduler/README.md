# 更新排程邏輯原型（用完即丟）

**這不是正式框架排程器，也不是 API 提案。** 只用來回答：

> 固定輪成員＋混合額度續排，能否同時保住「直接值立即可讀」「通知不遞迴且順序可預期」「安全時才提交結構」「非阻塞關閉且不遺失已受理工作」？

依據 ADR 0002／0003 與 `docs/research/scheduler-budget-continuation-shutdown.md`。v1 證據已被取代（見 `evidence/SUPERSEDED-v1.txt`）。
**v3** 補上兩個生命週期漏洞（見下方「v3 修正」）；最新證據是 `scenarios-v3.log`、`benchmark-v3-*`。v2 檔案保留，但不包含 v3 的修正。下方的 benchmark 表是 v2 的數字；v3 沒有改變計時涵蓋的範圍。

## 檔案

- `scheduler_model.hpp`：可攜的邏輯模型（`Env`、`Host`、`Mailbox`），不含 Win32。
- `main.cpp`：`--scenarios`（模擬時鐘，自我檢查）、`--benchmark`（steady_clock＋原生執行緒）、`--interactive`（Win32 小視窗）。
- `run.ps1`：`-BuildOnly`／`-Scenarios`／`-Benchmark`／`-Interactive`，四選一。獨立 CMake 建置在 `build/`，輸出寫到 `evidence/`。

## 模型中的規則（含 fixture 選擇）

- **普通入口**（設定值、建立／重建目標、送事件、移除、啟動操作）在範圍不是執行中時全部拒絕，**不改任何狀態、不取得租用**。`start_op` 對不存在、待移除或已移除的目標也拒絕。
- **完成通道**是內部入口：收尾中仍接受。
- 直接值設定後立即存入；通知一律排入**下一輪**，每個鍵在下一輪只留一個（合併）。
- 新一輪開始時把下一輪清單整份搬入，**成員固定**。
- 每片處理在**每個工作單位開始前**檢查「工作數或經過時間」，先到者讓出；已開始的單位不會被中斷。下列每一種都算一項工作：
  - 處理一封完成信（包括未知或重複的信）
  - 派送一則通知或事件（包括拒絕遞送）
  - 提交結構
  - 開始新一輪
- 本輪全部派送完、而且沒有派送在堆疊上（`depth==0`）、也沒有外層遍歷（`outer_traversals==0`）時，才先提交待移除的結構，**再**開始下一輪。外層遍歷仍在時，兩者都暫停（停止原因「提交等待外層遍歷」）。
- 移除受理後目標立即為「待移除」並拒絕新操作；已排入的事件在派送時檢查目標狀態與世代，不符就**拒絕遞送**（計數、留紀錄，不是丟棄）。
- 重入：派送中再呼叫同一環境的處理，只記錄**一個**待喚醒，不遞迴也不重複排入。
- 關閉：拒絕普通新工作、目標失效、送出取消請求（不代表成功）。超過診斷期限只標「逾期」，狀態仍是收尾中；所有操作結算、租用歸還後才變成已關閉。結果不回寫失效或世代不符的目標。
- **Host fixture 政策**（不是正式佇列政策）：每一步最多從信箱收 `admit_limit`（預設 8）封，依環境 id 送進各環境的收件匣，剩下的留在信箱；之後依輪流順序給一個環境一片處理。
- 額度參數必須「至少 1 項且大於 0 毫秒」，否則直接拒絕，避免無聲空轉。
- **fixture 選擇**：本輪後段已有 B 通知時又設定 B，不會消耗本輪那一筆，下一輪會再通知一次（情境1b 觀察到 2 次）。去重政策未定。

## v3 修正

- **關閉後不再遞送一般 UI 通知**：通知被派送前，先檢查範圍是否仍在執行中。若不是，就不呼叫回呼，計為「抑制」，不算遺失事件；事件仍各自保留它的處理結果。若是回呼自己呼叫了 `close()`，該回呼照常返回。
- **關閉收尾也受「使用中」防護**：只要派送在堆疊上、處理片正在執行、或外層遍歷仍在進行，就不會進入已關閉，也不會釋放環境租用。這和提交結構用的是同一套防護。
- **情境6**（`scenarios-v3.log`，全部 PASS）：
  - **6a**：關閉前已排入的通知不遞送；哨兵計數維持 0，範圍照常收尾並關閉。
  - **6b**：回呼內呼叫關閉，該回呼正常返回；同一輪後面的通知不遞送。
  - **6c**：沒有目標的環境，外層遍歷仍在時保持收尾中、租用保留；遍歷結束後才關閉並釋放租用。
- v3 的 benchmark（`benchmark-v3-*`）failures=0。

## 情境結果（`evidence/scenarios-v2.log`，v3 也全部重跑通過，模擬時鐘，不是效能）

全部 PASS（failures=0）：
1. **情境1**：回呼內 `B=1` 立即讀到 1；C 立即待移除並拒絕新操作；B 兩次設定合併；第 1 輪中途因額度讓出時 C 尚未提交；C 的事件拒絕遞送、D 的事件執行；下一輪 B 通知讀到 2，而且 C 的移除已在它之前提交；已受理 = 執行 + 拒絕遞送，丟棄 0，沒有剩餘；最大派送深度 1。
2. **情境2**：工作數額度 3（輪開始 1 項＋通知 2 項）；時間額度 2.5 ms 在第 3 個通知（3 ms）後讓出；7 ms 長回呼正常返回（軟限制）；兩次重入要求只留一個待喚醒、只續排一次。**2b**：0 毫秒或 0 項的額度被拒絕。
3. **情境3**：舊世代結果被拒絕；`start_op` 對三種無效目標都拒絕且不取得租用；收尾中 6 個普通入口全部拒絕，前後狀態快照完全相同；B 持續；逾期但仍是收尾中；送達完成後才關閉；B 繼續使用共用服務。
4. **情境4（信箱灌爆）**：每片 A 最多 4 項（含完成處理），每步最多收 8 封；39 封未知完成被計數拒絕、1 封被接受；B 的 20 個事件全部執行；A 輪中讓出不提交。
5. **情境5（輪尾用完額度）**：額度剛好在本輪結束時用完 → 不提交、不開始下一輪；外層遍歷仍在 → 照樣暫停；外層結束後先提交再開始下一輪，下一輪的 Z 通知看到已提交。

- **計入每片時間**：額度檢查、完成處理、通知／事件派送（含拒絕遞送）、提交、開始新一輪。
- **Host 一步**另外包含：有上限的信箱收取，以及收尾狀態檢查。
- 0.5 ms／16 那組有 2 片先碰到工作數上限。推測是處理 20 封便宜的未知完成信的片，但沒有逐片驗證，CSV 可以對照。
- **長回呼示範**（另外列出，不和上面的組合一起算百分位）：額度 0.5 ms／16，第一個事件跑 5 ms → 該片 5.000 ms（含開始新一輪共 2 項），下一片 0.5 ms；之後處理完，核對 PASS。額度是軟限制。

**原生執行緒關閉示範**：
- 兩個有限的 `std::thread`：一個故意忽略取消（60 次 `sleep_for(1ms)`），一個合作式。
- 擁有者執行緒一直排程，直到 A 已關閉**而且**兩個 worker 都回報 finished 才停；之後才 join，沒有 detach。5 秒看門狗只回報診斷，不強制釋放。
- 實際觀察時間：關閉要求 11.4 ms、逾期 41.9 ms、已關閉 920.0 ms。這些是這次的觀察值，受 OS 排程影響，不是保證。
- 檢查通過：收到 2 個完成；**拒絕回寫**失效目標 2 次；失效目標的值維持 0；A 收尾期間 B 實際執行了 59 個事件；逾期之後共用服務租用仍是 2（一個操作還持有）；結束時剩 1（B）。

## 限制

- 互動模式是真的原生 Win32 視窗（按鈕和清單），但排程模型本身只在單一 owner 執行緒上運作。宿主巢狀迴圈、模態對話框、重入相容性只在模型裡模擬（外層遍歷計數器、待喚醒）。沒有測試真實宿主迴圈、UIA 或 IME。
- 「外層遍歷」是 fixture 計數器；「等外層退出後再續排」由 Host 的下一次呼叫代替，沒有宿主契約。
- 公平性只有簡單輪流，沒有優先級；信箱收取上限是 fixture 選擇。
- 很大的固定輪仍會延後提交（模型沒有解決這點，ADR 0003 也已承認）。
- 數值都是探索用，不是建議預設值，也沒有任何延遲保證；benchmark 的工作成本是人為的。
