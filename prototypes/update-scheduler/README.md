# 更新排程邏輯原型（用完即丟）v4

**這不是正式框架排程器，也不是 API 提案。** v4 在 v3 的基礎上，回答 ADR 0003 新決定留下的問題：

> 持續超載時，普通工作容量有上限、已預留的終態結果仍能結算、同環境內收尾與普通工作不互相餓死、多環境輪替、收尾中容量能正確歸還——這些能否在同一個模型裡同時成立？

v1、v2 證據已被取代（`evidence/SUPERSEDED-v1.txt`）；v3、v4 證據保留作歷史紀錄；**最新是 `scenarios-v5.log`、`benchmark-v5-*`**。

## v5 修正（審查後）

- **跨帳本 token 撞號**：先抓到紅燈（`evidence/scenarios-v5-red-token.log`，failures=3）。兩個新帳本都發出「槽位 0、世代 1」的 token，A 的 token 能在 B 的帳本發布成功。
  - 修正：每個帳本從一個只增不減的程序內計數器取得編號，token 帶著這個編號；`publish` 和 `cancel_requested` 都會拒絕外來 token。新建立的帳本也不接受舊帳本的 token。
  - 這是**實驗性**的身分做法，不是安全機制或 ABI 設計。
- **單獨驗證目標世代**（情境12）：範圍**一直在執行中**；目標先移除、再以世代 2 重建，之後舊操作的結果才送達。結果因世代不符被拒絕，新目標的值不變，槽位和租用各歸還一次。同時加回 `start_op` 對三種無效目標的檢查，以及終態容量 0 和 1 的邊界。
- **公平性證據**：
  - 改成在生產期間（drain 之前）量測**實際事件遞送**（派送或拒絕遞送），和內部普通單位（提交、開始新一輪）分開報告。
  - 觀察值（額度 1／2／3 項）：A 兩次遞送之間最多隔 5 個工作單位，換算成 host 步分別最多 11／5／3 步。
  - 生產期間 A 實際遞送 322／645／969 個事件，B 實際執行 956／1000／1000 個。
  - 內部普通單位的最大等待是 2。這些都是觀察值，不是普遍保證。
- **實際儲存量的說法更正**：普通容量計算的是**邏輯佔用**。本輪的 vector 會保留已處理過的前段，直到開始下一輪，所以兩個 vector 實際保留的 Work 記錄最多接近 2×容量。
  - 情境7b 實測：邏輯佔用峰值 16；實際保留記錄峰值 30；兩個 vector 配置容量合計 32；長時間執行沒有成長。
  - 這不是整個程式的記憶體保證。
- `accounted()` 改用**獨立掃描佇列**得到的待處理數（並檢查它和模型的增量計數一致），避免檢查變成恆等式。
- 互動模式狀態列加上 B 的普通容量和終態槽位。滿載中關閉的引導流程，在最後一個預留結果結算前都顯示收尾中。這項介面修改在 v5 測試之後才做，只動到顯示，已重新建置。

## 檔案

- `scheduler_model.hpp`：邏輯模型（`Env`、`Host`、`TerminalLedger`），不含 Win32。
- `main.cpp`：`--scenarios`（模擬時鐘，自我檢查）、`--benchmark`（steady_clock＋原生執行緒）、`--interactive`（Win32 視窗）。

## 帳本與不變式

每個環境有兩種容量，都只由一個地方計算：

- **普通容量**（`ordinary_cap`）：計算「已受理、還沒處理完」的普通項目，包括本輪剩餘、下一輪，以及正在執行的那一項。
  - 滿載時，`post_event` 和需要新通知的 `set` 都回報**未受理**，而且在改值之前就拒絕，所以值和佇列都不變。
  - 如果下一輪已經有同一個鍵的通知，`set` 可以合併受理、值立即更新，不佔新容量。
  - 容量 0 是明確政策：一律未受理。
  - 不變式：提供 = 受理 + 未受理；受理事件 = 執行 + 拒絕遞送 + 待處理。
- **終態槽位**（`TerminalLedger`）：固定大小的槽位陣列，加上同樣大小的環形就緒佇列，建立時一次配置。
  - **啟動操作前**先預留一個槽位；預留不到就不啟動，也不取得共用服務租用。租用跟著槽位走。
  - 狀態流程：空 → 已預留 → 已發布 → 結算後才歸還（不是發布時歸還），歸還時世代前進。
  - token 是「槽位編號＋世代」。worker 只持有帳本指標和 token，不碰 UI。
  - 未知槽位、舊世代、重複發布都直接拒絕並計數，**不配置任何額外儲存**。一個槽位在「已預留」時只能發布一次，所以就緒佇列不會溢位。
  - 完成過的操作不另外保存紀錄；儲存量就是固定的槽位數。
- **移除與失效**用另一份 teardown 資料（每個目標最多一筆），不佔普通容量，所以普通佇列滿了也擋不住移除或關閉。

## 排程規則（fixture 選擇，不是正式預設）

- 每一片處理：先檢查額度；接著若有就緒結果，而且「收尾連續數 < 配額（預設 2）」或「普通工作此刻無法前進」，就結算一個結果；否則推進一個普通單位（派送一項、提交、或開始新一輪）。
- **收尾連續數跨片保存**：額度設成 1 也不會被每片重設，所以普通工作不會被餓死。推進普通單位時歸零。
- 多環境：Host 依輪流順序給有工作的環境一片處理。
- 其他規則沿用 v3：固定輪成員、先提交再下一輪、外層遍歷防護、關閉後不遞送通知、收尾逾期仍是收尾中。

## 情境結果（v4 紀錄；v5 全部重跑通過，見 `evidence/scenarios-v5.log`，模擬時鐘，不是效能）

- v3 情境 1、2、5、6 改接新帳本後重跑，全部通過。
- **情境7（容量）**：容量 4 佔滿後，事件和新通知的設定都未受理、狀態快照不變；可合併的設定照樣受理；處理一步後本輪剩餘仍計入佔用；釋出後恢復受理。容量 1、容量 0 的邊界也檢查過。
- **情境7b（持續超載 600 步）**：生產者每步提供 5 項，消費額度每步 3 項，容量 16。
  - 提供 3000＝受理 1132＋未受理 1868。
  - 每一步的邏輯佔用、本輪記錄數、下一輪記錄數，**各自**都不超過 16；兩者合計的實際保留量見 v5 修正。
  - 停止生產後處理完：受理＝執行，剩餘 0。
  - B 的 200 個事件全部執行。
- **情境8（終態預留）**：
  - 第 4 個操作因槽位滿而不啟動，也不取得租用。
  - 普通容量全滿時，已預留的結果仍能發布並結算。
  - 未知、舊世代、重複的發布都被拒絕，不增加儲存。
  - 槽位可重用，舊 token 失效；目標先被移除再重建後，晚到結果也不回寫。
  - 收尾中仍接受有效結果；每個槽位只歸還一次。
  - 3000 次「預留→發布→結算」循環後，槽位和環形佇列仍是固定 3 格。
- **情境9（持續混合流量 2000 步，額度 1／2／3 項）**：每步都有新的普通事件、新的完成結果，以及 5 次偽造發布。
  - 觀察到 A 的普通工作最大連續等待 2 個工作單位（等於配額）。
  - 在有結果待結算時，A 的普通工作仍持續前進。
  - B 有工作時最多等 1 個 host 步；B 的 1000 個事件全部執行。
  - 10000 次偽造發布全部被拒絕，就緒佇列從不超過槽位數。
  - 以上都是這個 fixture 下的**觀察值**，不是普遍保證。
- **情境10（滿載中關閉）**：
  - 普通容量滿、3 個預留操作都還在時關閉。普通受理和啟動操作都被拒絕，狀態不變。
  - 逾期時仍是收尾中，3 個槽位和租用都保留。
  - 收到兩個有效結果後，只保留 1 槽 1 租用；第三個 worker 尚未發布時仍是收尾中。
  - 重複發布無害地被拒絕；第三個結果發布後全部結算，才變成已關閉。
  - 關閉前已受理的 4 個事件都有處理結果（拒絕遞送）；B 繼續執行。

## Benchmark（下表為 v4 數字；v5 重跑 failures=0，見 `evidence/benchmark-v5-summary.log`、`benchmark-v5-slices.csv`）

steady_clock 量到的 CPU 時間；工作成本是**人為的 50 µs busy-wait**。

- **計入每片**：額度檢查、終態結算、派送（含拒絕遞送）、提交、開始新一輪。
- **Host 一步**另外包含收尾狀態檢查。
- 生產者提供工作和發布結果都發生在兩步**之間**，不在任何計時範圍內。
- 每組取樣 40 片 A，之後在量測之外處理完，並驗證：計帳一致、剩餘 0、槽位全部歸還、租用為 0、峰值佔用不超過容量。

## 互動模式（Codex 幫使用者開啟；模擬時鐘）

三排按鈕都在視窗內：
- 情境1、超載、混合流量、滿載中關閉、重設
- 單步一片、加負載（A 8 項）、B送事件、A啟動操作/送事件
- 發布一個結果、偽造發布、關閉A

狀態列顯示：
- A 普通容量的已用／空、終態槽位的已用／空、待結算數、收尾連續數。
- 提供／受理／未受理、事件的執行／拒絕遞送／待處理。
- 操作的啟動／未啟動／結算、拒絕發布數、B 事件數、共用服務租用數。

我沒有開啟互動模式。

## 限制

- 容量、配額、額度都是探索用的 fixture 數值，不是正式預設。
- 公平性只觀察了「兩個環境、固定成本」的情境；長回呼或宿主阻塞時不推論牆鐘公平。
- 結果資料是固定的小結構，不代表任意大小的結果都能放進 UI 記憶體。
- 互動模式是真的 Win32 視窗，但宿主巢狀迴圈、模態對話框、UIA、IME 都沒有涵蓋。
- 很大的固定輪仍會延後提交；可等待容量的介面、跨環境配額和權重都沒有實作。
