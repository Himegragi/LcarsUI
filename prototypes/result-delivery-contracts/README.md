# 可丟棄原型 v4：Q135–Q138 結果交付契約

**用完即丟、純模擬。**不是框架程式碼，也不是 API 提案。開啟 `integrated-v4.html` 即可。

以 `prototypes/handoff-recovery-integration/integrated.html`（v3，`07c2a33`）複製後修改。v3 與其 Codex 驗證紀錄保持原樣；v3 的證據不適用於本版，本版的證據也不回頭證明 v3。

## 問題
ADR 0003 於 2026-10-11 選定的四項契約，在 v3 整合模型上能否同時成立：
- **Q135**：承擔義務前先預留必要結束回報的保存位置；容量不足就不承擔；已承擔義務的回報不因控制通道與重送票滿載而「未保留」。
- **Q136**：結果責任結清前，原執行作用範圍維持收尾中；視覺關閉不算結清。
- **Q137**：一般結果的承接成立點由各接收契約明確定義；框架拒絕未寫明的契約。
- **Q138**：擁有者可明確放棄未交付結果；逾時、關閉、停止派送都不算放棄；需收尾安全；留下可與「已交付」區分的紀錄；不影響必要故障交接。

## v4 相對 v3 的改變（fixture 安排，未核定為公開介面）
- 新增「必要回報預留」池（fixture 上限 10）。開始命令預留 1；遞送交接預留 3（回呼結束、工作結束、租用歸還）。不足時拒絕。
- `postControl`：身分有效、對應義務仍存在、該預留尚未被填的回報，存入預留位置；處理時優先於一般控制訊息。重複或無效訊息仍走 v3 的一般控制／重送票路徑，可能「未保留」。停止派送時仍可存入，但不結算。
- `finalizeClosed`：環境仍有回條（未交付或未放棄的結果）時不結束。
- 每個環境啟用時必須帶接收契約：A、B 為「交出即承接」，C 為「逐筆明確確認」。`collectReceipts` 依契約處理；C 需另送 `resultAck`。
- `abandonResults`：擁有者明確動作；收尾不安全時拒絕；只處置已終態的結果；寫入有界的結清紀錄（`outcomes`，fixture 上限 40）。
- 新增不變式：每個進行中命令／回呼／列管工作／租用都有回報預留；每個預留都對應存活義務；已結束範圍不得持有回條；同一結果只有一筆結清紀錄。
- 舊引導 1、3、5 的預期依新契約調整（見下方）；新增引導 7（Q135）、8（Q136／Q137）、9（Q138）。

### 舊預期的刻意改變
- 引導 1：A 安全收尾後維持「收尾中」，直到接收方取走結果；交接額度在取走時才全部歸還。
- 引導 3：控制與重送票都滿時，有效的租用歸還改為「存入預留位置」，不再「未保留」；無效訊息從 8 則增為 11 則，才能維持「兩者皆滿」的情境。原「呼叫端之後重送」改為重複訊息，應被忽略。
- 引導 5：A 安全收尾後仍收尾中（回條未交付）；停止派送時的回呼結束改為存入預留位置。

## 限制
- 預留池是單一共用池；實際的保存、喚醒、容量歸還機制仍待研究（ADR 0003 Q135 原文）。
- 「收尾安全」仍是宣告，不是偵測。
- 結清紀錄有上限且會淘汰最舊項目；真正需要保留多久未決定。
- 交接的 `ack` 仍走一般控制通道，未納入回報預留；Q135 只涵蓋已承擔義務的結束回報。
- 結果確認 `resultAck` 走一般控制通道，可能因滿載而未保留；這代表承接尚未成立，範圍會繼續收尾中。
- 沒有真實宿主、執行緒、C++ 生命週期、GPU 或效能保證。
